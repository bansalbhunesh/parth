# PS4 External Benchmark — Error Analysis (v1.2)

Source: the saved **3-pass `google/gemini-3.1-flash-lite`** integrated run
(grounding + vision + retry in pipeline). **Analysis only** — regenerated by
`python scripts/benchmark_error_analysis.py` from predictions already on disk;
no API calls, no change to scoring or prompts. Per-item detail:
[`false_positives.csv`](false_positives.csv) · [`false_negatives.csv`](false_negatives.csv).

Totals across the 3 passes: **8 false positives, 26 false negatives** (positive
denominator 63/pass; mean recall 0.862, precision 0.953, clean-negative FAR 0.000).

| duplicate/over-broad · wrong component · adversarial confusion · schedule overreach | 0 | — |

**None of the 8 FPs is the model inventing a deviation.** They are all cases
where the model found the *right* deviation but the one-to-one semantic scorer
could not credit it:

- **`pair_005` / `pair_022` (unit representation):** the model correctly converts
  (`4000 m³/h ≈ 2354 CFM < 2500`; `4 s = 4000 ms > 100 ms`) and reports the
  *converted* value, but the label stores the *raw* value, so the matcher sees
  two different strings. This is the **same event** as the "unit conversion
  missed" false negatives below — one model action, double-counted by the scorer.
- **`pair_020` (weak label):** the model's `"both Modbus and BACnet" → "BACnet
  only"` is *more* precise than the label's `"supported"/"not supported"`. This
  is the exact label the automated audit flagged (`P020-L03`).

## Top causes, ranked

1. **Omission under-detection (top real FN cause).** The lite model reliably
   catches value/categorical/derived/adversarial/image cases but under-reports
   *omissions* — when a required item is simply absent from the submittal it is
   flagged only ~3/8 of the time. This is a genuine **prompt/model** gap.
2. **Unit-representation scorer/label mismatch (top FP cause, and a chunk of FNs).**
   The model converts correctly; the label and matcher disagree on representation.
   This is a **scorer / benchmark-label** issue, not a model error.
3. **One weakly-phrased label (`pair_020`).** A **benchmark-label** issue already
   surfaced by the automated audit.
4. **Transient provider errors** on ~1 pair/3-passes → recorded `not_run` (counted
   as a miss). **Infra**, not model.

## Repeated failure patterns
- The **same 5 omission labels** miss in all 3 passes → systematic, not noise.
- `pair_005` appears as both an FP and an FN in every pass → a single
  unit-conversion representation clash counted twice.
- `pair_020` mis-scores every pass → one weak label, not model drift.

## What was already fixed this cycle
- **Hallucinated-requirement FPs → 0** (grounding filter; was ~29/pass pre-fix).
- **Clean-negative FAR → 0.000** (grounding).
- **Image/vision 0/6 → 6/6** (OpenAI-compat vision path).
- **60 s timeouts → gone** (`PRAMAAN_LLM_TIMEOUT=150`); transient retry added.

## What remains (and who owns it)
- **Omission recall** — a prompt/model improvement (prompt emphasis on "flag
  every required item the submittal does not address"). Candidate for a *future*
  prompt pass, measured on this benchmark.
- **Unit-conversion reconciliation** — a **benchmark-label / scorer** fix:
  store both raw and converted values on unit-conversion labels, or teach the
  matcher unit awareness. This is label-quality work (Phase 2B review), not a
  model change.
- **`pair_020` re-phrasing** — human review (Phase 2B), tracked by the audit.

## What must NOT be over-fit
- **Do not hand-tune the prompt or scorer to make `pair_005` / `pair_020` /
  `pair_022` pass.** Those are label/representation issues; "fixing" them by
  teaching to these exact pairs is over-fitting to the test.
- **Do not inflate omission recall by relabeling the 5 omission pairs as easier.**
  The gap is real and should be reported, not hidden.
- Keep reporting `not_run`/timeouts as misses in the primary metric.
